Week 4 · Software Engineer Discipline · Deep Dive

Software Engineer Field Guide

This guide gives an AI Solution Architect the roughly 20% of software engineering knowledge that matters most: not how to write every line of code by hand, but how to direct an AI coding agent with a clear design, evaluate what it produces against real engineering standards, and approve only what is genuinely shippable. Every concept below is made concrete using one running example — a fast-track claims triage feature for a fictional auto insurer, Meridian Mutual Insurance — and every one of the seven governance documents an architect is expected to sponsor is produced in full, in a professional, downloadable format.

How to use this guide Use the left navigation to jump between topics, the search box to find a specific term anywhere in the guide, or type a question into Ask the Field Guide for an instant answer drawn from this document’s own content. Every one of the seven documents in the Document Library can be downloaded as a standalone HTML file, printed to PDF, or (where tabular) exported to CSV.

Why Software Engineering Exists

Anyone can write a script that works once, on one machine, with one set of inputs. Software engineering is the discipline that makes a system work reliably, for many people, under changing conditions, for years, while other people modify it after the original author has moved on. It exists because business needs outlive the individuals who first encode them, and because the cost of a defect compounds with scale: a bug that costs one minute to fix in a design review can cost weeks to fix in production, and in a regulated domain like insurance it can cost a compliance finding, a customer harm claim, or a restated financial result.

An AI coding agent changes who writes the code, not why the discipline matters. A language model can generate a working claims-scoring function in seconds — but it has no stake in whether that function is still correct after the underwriting rules change next quarter, no memory of why a previous version broke in production, and no accountability when it silently swallows an exception. That gap is exactly what an AI Solution Architect is there to close. You do not need to write every line by hand. You need enough engineering judgment to direct the agent with an unambiguous design, evaluate its output against real standards, and approve only what will actually hold up in production.

The core risk this guide addresses AI-generated code that "looks right" and passes a quick manual test is not the same as code that is correct, secure, and maintainable. Without engineering discipline, an AI agent will happily produce code with silent failure paths, untyped contracts, and no tests — and it will do so with total confidence. Your job is to be the check on that confidence.

The 20% You Need to Know

These nine ideas cover the vast majority of what actually determines whether AI-generated code is safe to ship. You will see every one of them applied to a single running example — Meridian Mutual’s claims fast-track triage feature — throughout the rest of this guide.

Technical design documents come first

Code is the last artifact produced, not the first. A Technical Design Document (TDD) forces the hard thinking — what problem is being solved, what approach was chosen and why, what the module boundaries and data model look like, what could go wrong — to happen on paper, where it is cheap to change, instead of in code, where it is expensive to change. When you direct an AI agent, the TDD is the brief you hand it; when you evaluate its output, the TDD is the spec you check it against. No design document means no way to tell whether the AI built the right thing.

Modularity and separation of concerns

A well-designed system is built from modules that each do one job and expose it through a narrow, well-defined boundary. A module named RiskScoringEngine should score risk — it should not also send notification emails, write audit logs, or decide which adjuster queue a claim lands in. When responsibilities are separated, a change to notification wording cannot accidentally break risk scoring, two engineers (or two AI sessions) can work on different modules without colliding, and a reviewer can understand one module without reading the whole system.

What to watch for in AI output AI agents tend to produce one large function that does "the whole thing" because that is the easiest way to satisfy a prompt end-to-end. If a generated module has more than five or six public responsibilities, or its name needs the word "and" to describe what it does, send it back for a split.

Interfaces and contracts

An interface is a promise: given these inputs, in this shape, I will return this output, in this shape, or fail in one of these specific, named ways. A contract is that promise made explicit and checkable — typically as a type signature plus documented error cases. Contracts are what let modules be built, tested, and reviewed independently. If TriageDecisionEngine.decide() has an explicit contract, you can approve it without reading RiskScoringEngine’s internals at all — you only need to trust that it honors its side of the contract.

Clean code and naming

Code is read far more often than it is written, and a name is the cheapest documentation that exists. calc(x, y, t) tells a reviewer nothing; calculateRiskScore(claim, policyRiskTier) tells a reviewer almost everything without a single comment. Clean code favors small functions with a single level of abstraction, names that reveal intent, and structure that makes the "happy path" visually obvious. When reviewing AI output, unclear naming is not a cosmetic nitpick — it is a leading indicator that the underlying logic was not thought through cleanly either.

Version control, branching, and code review

Git is the system of record for every change and every decision about that change. Small, well-scoped commits and pull requests let a human reviewer actually hold the change in their head; a 2,000-line AI-generated PR cannot be meaningfully reviewed by anyone, which means it cannot be meaningfully approved. Code review is the formal checkpoint where a second party — a human architect, in this accelerator’s model — verifies that a change meets the bar before it merges. AI-generated code does not get a pass on this step; if anything it needs it more, because no one "remembers" the reasoning behind a change an AI wrote unless the PR description captures it.

The testing pyramid

Tests are not an afterthought bolted onto finished code — they are how "it works" becomes a falsifiable, repeatable claim instead of an opinion. The testing pyramid describes the healthy mix: many fast, cheap unit tests for pure logic; a smaller number of integration tests that verify modules work together against a real (non-production) database or mock external service; and a thin layer of end-to-end tests that verify the whole user-facing flow through a real browser or API client. A suite with more E2E tests than unit tests is inverted, slow, and flaky — a process violation, not a sign of thoroughness.

Technical debt

Technical debt is a shortcut taken today that has to be "repaid" later with interest — extra effort spent working around the shortcut until it is fixed. Some debt is a deliberate, logged trade-off (ship the fast-track threshold as a hardcoded constant this sprint, replace it with a configurable rule engine next sprint); undisclosed debt is far more dangerous, because nobody downstream knows the shortcut exists until it breaks. AI agents accumulate debt invisibly — they will happily hardcode a value, skip a validation, or duplicate a block of logic without ever flagging that they did so. Part of the review lens is actively hunting for debt the AI did not disclose.

DRY and SOLID, lightly

DRY (Don’t Repeat Yourself) says that every piece of knowledge should have a single, authoritative representation in the system — if the fast-track claim-amount threshold is defined in three files, a policy change requires editing three files correctly, and eventually one gets missed. You do not need to recite all five SOLID principles to review AI code well, but two carry outsized weight:

  • Single Responsibility — a class or module should have one reason to change. This is modularity applied at the class level.
  • Dependency Inversion — high-level modules (like TriageDecisionEngine) should depend on an abstraction (like a RiskScoringPort interface), not on a concrete implementation (a specific ML model client). This is what lets you swap the risk model later without rewriting the decision logic, and what makes a module testable without a real network call.

Error handling

How a system behaves when something goes wrong is at least as important as how it behaves when everything goes right — arguably more so, because failure paths are exercised under the worst possible conditions (an outage, a spike in traffic, a malicious input) and are the least tested by default. The one rule that matters most: a caught exception must never disappear silently. It must be logged with enough context to diagnose it, classified with a stable error type, and either recovered from or surfaced — never swallowed.

Reject — silent swallow
try { const score = callRiskModel(claim); return score; } catch (e) { // swallowed - caller has no idea this failed return null; }
Approve — classified & surfaced
try { const score = await callRiskModel(claim, { timeoutMs: 8000 }); return score; } catch (e) { logger.error({ event: "risk_model_call_failed", error_class: classify(e), // e.g. "TimeoutError" claimId: claim.id, }); throw new UpstreamUnavailableError("risk-model", e); }

Good vs. Bad Code

Four everyday examples, each drawn from the claims triage domain, that show what separates code an architect should approve from code that should bounce back to the agent.

1. Naming that reveals intent

Reject
function chk(c, p) { if (c.amt < p.t && c.rt < 3) { return true; } return false; }
Approve
function isEligibleForFastTrack( claim: ValidatedClaim, policy: PolicyRecord ): boolean { return claim.estimatedAmount < policy.fastTrackThreshold && claim.riskTier < RISK_TIER_MANUAL_REVIEW_FLOOR; }

2. Single responsibility vs. a "god function"

Reject
// validates, scores, decides, queues, // e-mails, and logs — all in one function async function handleClaim(req, res) { // 140 lines doing six jobs... }
Approve
const claim = await validator.validate(raw); const score = await scorer.score(claim, policy); const decision = decider.decide(score, policy); await router.route(claim, decision); await auditLogger.record({claim, decision});

3. Typed, validated boundaries vs. trusting raw input

Reject
app.post("/claims", (req, res) => { const claim = req.body; // any, unvalidated db.insert("claims", claim); // trusts caller });
Approve
app.post("/claims", validateBody(RawClaimSchema), async (req, res) => { const claim: RawClaimSubmission = req.body; const result = await intake.handle(claim); res.status(201).json(result); });

4. Idempotency vs. accidental duplication

Reject
// retried webhook = duplicate queue ticket async function enqueue(claim, decision) { return db.insert("adjuster_queue", { claimId: claim.id, decision }); }
Approve
async function enqueue(claim, decision) { return db.query(`INSERT INTO adjuster_queue (claim_id, decision, idempotency_key) VALUES ($1, $2, $3) ON CONFLICT (idempotency_key) DO NOTHING`, [claim.id, decision, buildKey(claim.id)]); }

The Architect’s Review Lens

Before approving any AI-generated pull request, run it through these seven questions in order. If you cannot answer "yes" to all seven, the change is not ready — regardless of how polished the code looks.

#QuestionWhat "no" looks like
1Does this match the approved design document?AI silently changed the approach, added scope, or skipped a module in the TDD.
2Is every module’s responsibility single and its contract explicit?One function validates, scores, and notifies; inputs/outputs are untyped.
3Does every failure path do something other than nothing?An empty catch block, or a generic Error with no classification.
4Is the change safe to run twice?A retried request creates a second queue ticket or sends a duplicate email.
5Do tests assert behavior, including failure and boundary cases?Only the happy path is tested; no test simulates a timeout or malformed input.
6Are names, structure, and file size legible to a junior developer?Cryptic abbreviations, 400+ line files, unclear branching logic.
7Is anything here a governance boundary — schema change, new external dependency, compliance surface?If yes, this needs escalation before merge, not just review.
Why this order matters Questions 1–2 catch scope and design drift before you spend time on code-level detail. Questions 3–6 are the Build-Break-Harden checks. Question 7 is the last gate specifically because it can override every "yes" that came before it — a perfectly engineered change can still need escalation if it crosses a governance line.
Worked Example · Insurance

Meridian Mutual Insurance: Claims Fast-Track Triage

Every document in the library below is written for this one feature. Read this section once and the seven documents that follow will read as a coherent set, not seven disconnected samples.

The business problem

Meridian Mutual is a mid-size auto insurer. Every incoming claim currently goes to a human adjuster queue, regardless of size or complexity — a $600 bumper repair with a clean policy history waits in the same queue as a multi-vehicle injury claim. The adjuster team is 40% over its target caseload, the average claim now takes 9.4 days to first contact against an 5-day SLA, and Meridian is paying overtime and losing customers to faster competitors on exactly the claims that should be the easiest to close.

The feature

The Claims Fast-Track Triage Service automatically classifies every newly submitted auto claim into one of two lanes the moment it is received:

  • FAST_TRACK — low estimated amount, clean policy risk tier, no prior flags — is auto-approved for expedited payment processing with no adjuster in the loop.
  • MANUAL_REVIEW — everything else — is routed to the existing adjuster queue, now prioritized by a risk score instead of arrival order.

The classification is a hybrid of deterministic underwriting rules (amount thresholds, coverage type) and a risk-scoring model informed by policy history. The decision, and every input that produced it, is written to an immutable audit trail — required both for internal QA and for state insurance regulators who can request the basis for any auto-approval.

Why this is a good teaching example It has a real data model (policies, claims, decisions, adjusters), a real main flow worth diagramming, genuine failure modes (a risk model timeout must not silently auto-approve a claim), a hard idempotency requirement (a retried submission must not create two decisions), and a real compliance angle (the audit trail). It is exactly the shape of feature an AI Solution Architect will actually be asked to direct.

1. Purpose & Context

Meridian Mutual’s adjuster team is 40% over target caseload; average time-to-first-contact on auto claims is 9.4 days against a 5-day SLA. Roughly 55% of incoming claims are low-severity, low-amount, clean-history claims that historically resolve without dispute — but they currently wait in the same undifferentiated queue as complex, high-severity claims. This document specifies the design of a service that automatically fast-tracks that low-risk 55% at intake, freeing adjuster capacity for claims that genuinely need human judgment.

2. Goals & Non-Goals

In scope (Goals)Out of scope (Non-Goals)
Classify every new auto claim as FAST_TRACK or MANUAL_REVIEW within 2 seconds of submission Fraud detection modeling (handled by the existing Special Investigations Unit pipeline)
Auto-approve FAST_TRACK claims for expedited payment processing with a full audit trail Automated claims payment issuance — this service only authorizes the fast-track lane; issuance remains in the existing Payments service
Prioritize the MANUAL_REVIEW queue by computed risk score instead of arrival order Property, life, or commercial lines — auto only in this phase
Produce a defensible, replayable audit record for every decision (regulatory requirement) Real-time re-scoring of claims already in the adjuster queue

3. Chosen Approach

A hybrid rules-plus-model approach was selected over a pure rules engine or a pure ML classifier. Deterministic underwriting rules (coverage type eligibility, hard amount ceiling, policy standing) run first and can immediately force MANUAL_REVIEW — these are the rules a regulator or auditor must be able to read in plain English. A risk-scoring model then produces a continuous risk score for claims that pass the deterministic gate; a configurable threshold separates FAST_TRACK from MANUAL_REVIEW, and a narrow band just below that threshold is deliberately routed to a fast-lane human review rather than fully automated, as a safety margin while the model is new.

Design principle applied Dependency Inversion: TriageDecisionEngine depends on a RiskScore value object and a RiskScoringPort interface, not on the concrete risk model client. The model can be retrained, swapped for a vendor API, or rolled back to rules-only without touching decision logic.

  3. General availability: full rollout once canary loss ratio and defect rate hold within target for two consecutive weeks.

Every module below follows the Contract Enforcement rule: typed inputs, typed outputs, and every error condition named as a distinct type — never a bare Error. A module is approvable only if a reviewer can understand what it promises without reading its internals.

2.1 ClaimIntakeValidator

Responsibility: validate and normalize a raw HTTP claim submission into a typed, trustworthy internal representation. Nothing downstream re-validates this input.

interface ClaimIntakeValidator { validate(raw: RawClaimSubmission): Promise<ValidatedClaim>; } type RawClaimSubmission = { policyId: string; incidentType: "collision" | "comprehensive" | "liability"; estimatedAmountCents: number; incidentDate: string; // ISO-8601 description: string; }; type ValidatedClaim = RawClaimSubmission & { claimId: string; // server-assigned UUID v4 fingerprint: string; // dedup key, see AdjusterQueueService receivedAt: string; // ISO-8601, server clock }; // Throws — never returns null on failure class ValidationError extends Error { constructor(public fieldErrors: { field: string; reason: string }[]) { super("claim_validation_failed"); } }
Contract elementDetail
InputsRawClaimSubmission — validated against a Zod schema at the route boundary before this module is ever called
OutputsValidatedClaim — the only shape any downstream module is allowed to accept
ErrorsValidationError (400) — policy not found is PolicyNotFoundError (404), not folded into ValidationError
IdempotencyPure function of its input; no side effects; safe to call any number of times

2.2 RiskScoringEngine

Responsibility: produce a bounded, versioned risk score. Depends on an abstraction (RiskModelPort), never on a concrete vendor client — Dependency Inversion in practice.

interface RiskScoringEngine { score(claim: ValidatedClaim, policy: PolicyRecord): Promise<RiskScore>; } type RiskScore = { value: number; // 0-100, higher = riskier band: "LOW" | "MEDIUM" | "HIGH"; modelVersion: string; // e.g. "risk-v4.2.1" computedAt: string; }; interface RiskModelPort { // the abstraction RiskScoringEngine depends on predict(features: RiskFeatureVector): Promise<number>; } class UpstreamUnavailableError extends Error { constructor(public upstream: string, public cause: unknown) { super(`${upstream}_unavailable`); } }
Contract elementDetail
InputsValidatedClaim, PolicyRecord (fetched by caller, not this module — single responsibility)
OutputsRiskScore — always includes modelVersion for audit traceability
ErrorsUpstreamUnavailableError after 8s timeout + 2 retries (exponential backoff, 250ms base). Circuit breaker trips after 5 consecutive failures in a 60s window.
FallbackNone — on error, propagate. Caller (TriageDecisionEngine) fails closed to MANUAL_REVIEW; this module must never silently substitute a default score

2.3 TriageDecisionEngine

interface TriageDecisionEngine { decide(score: RiskScore, policy: PolicyRecord): TriageDecision; } type TriageDecision = { outcome: "FAST_TRACK" | "MANUAL_REVIEW"; reasonCodes: string[]; // e.g. ["AMOUNT_UNDER_THRESHOLD","RISK_TIER_1"] riskScoreValue: number; };
Contract elementDetail
InputsRiskScore, PolicyRecord
OutputsTriageDecision — pure, synchronous, deterministic given its inputs
ErrorsNone by design — this function cannot fail; it is a pure decision table over already-validated inputs. If score is missing, the caller never reaches this module (see RiskScoringEngine fallback rule)
Testability100% unit-testable with no mocks — the canonical example of why Dependency Inversion pays off

2.4 AdjusterQueueService

interface AdjusterQueueService { enqueue(claim: ValidatedClaim, decision: TriageDecision): Promise<QueueTicket>; } type QueueTicket = { ticketId: string; priority: number; queuedAt: string };
Contract elementDetail
IdempotencyUNIQUE(claim_id) constraint + ON CONFLICT DO NOTHING; a retried enqueue returns the existing ticket rather than erroring or duplicating
ErrorsDuplicateClaimError is not thrown — duplicate enqueue is a no-op success by design (see Idempotency, TDD Doc §7)

2.5 NotificationDispatcher

interface NotificationDispatcher { notify(decision: TriageDecision, claim: ValidatedClaim): Promise<DispatchResult>; } type DispatchResult = { sent: boolean; dedupeKey: string; provider: "mandrill" };
Contract elementDetail
IdempotencyDedup table keyed on (recipient, subject, claimId) checked before send, per the repo-wide Mandrill dedup pattern
ErrorsNotificationFailedError is logged and does not roll back the triage decision — the decision already happened and is already audited; a failed notification is retried by a dead-letter worker, not by re-running triage

2.6 AuditLogger

interface AuditLogger { record(event: AuditEvent): Promise<void>; } type AuditEvent = { entityType: "Claim" | "TriageDecision"; entityId: string; eventType: string; actor: "system:claims-triage-service"; payload: Record<string, unknown>; payloadHash: string; // SHA-256, tamper-evidence };
Contract elementDetail
GuaranteeCalled by every other module on every path, including error paths — a triage attempt that fails still produces an audit record
ErrorsIf the audit write itself fails, the whole request fails (fail-closed) — an unaudited auto-approval is treated as worse than a rejected request

3.3 TypeScript Strictness

  • strict: true in every tsconfig.json; tsc --noEmit must pass before merge.
  • any is forbidden without a comment on the same line explaining why (e.g. wrapping an untyped third-party SDK response before immediately validating it with Zod).
  • Every exported function has an explicit return type — inference is fine for locals, not for public contracts.
  • Discriminated unions over boolean flags: TriageDecision.outcome: "FAST_TRACK" | "MANUAL_REVIEW", never a loose isFastTrack: boolean plus a separate isManual: boolean that can disagree.

3.4 Comments

Default to no comments. A name that needs a comment to be understood should usually be renamed instead. Write a comment only for the why, never the what:

Reject
// loop through claims for (const c of claims) { ... }
Approve
// 8s timeout matches the risk-model SLA in TDD-2026-014 §7 const RISK_MODEL_TIMEOUT_MS = 8000;

3.5 Formatting & Linting

Prettier and ESLint run pre-commit via husky; a commit that fails either does not land. No manual style debates in code review — if the linter allows it, it is not a review comment.

3.6 Commit Messages

CLM-1234: add risk-score band to TriageDecision audit payload Regulators requested the numeric score alongside the outcome, not just the outcome, for post-hoc review of auto-approvals. Co-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>

First line: ticket key, imperative mood, under 70 characters. Body: the why, not a restatement of the diff. See Document 6 for the full branch-naming and PR convention this feeds into.

3.7 Configuration & Secrets

  • No hostnames, thresholds, or credentials hardcoded in source. FAST_TRACK_AMOUNT_CEILING_CENTS is an env-configured constant in v1 (see TDD §7 for the accepted-debt note on this).
  • process.env.RISK_MODEL_API_KEY is redacted (<redacted>) in every log line that touches it — enforced by a lint rule, not developer discipline alone.

Glossary

Every term below is used elsewhere in this guide; use the search box above if you want to jump straight to a term in context.

TDD (Technical Design Document)
The design artifact produced before code, covering context, chosen approach, module breakdown, data model, sequence, and risks.
SLA
Service Level Agreement — the committed performance bar, e.g. 5 days to first adjuster contact.
Idempotency
The property that running the same operation twice with the same input produces the same end state, with no duplicate side effects.
Circuit Breaker
A pattern that stops calling a failing upstream service after N consecutive failures, so the caller fails fast instead of hanging.
DRY
Don’t Repeat Yourself — every piece of knowledge should have one authoritative representation in the system.
SOLID
Five object-oriented design principles; this guide emphasizes Single Responsibility and Dependency Inversion.
Single Responsibility
A module or class should have exactly one reason to change.
Dependency Inversion
High-level modules depend on abstractions (interfaces), not on concrete implementations — lets you swap the risk model without rewriting decision logic.
Contract
A module’s explicit, typed promise: given these inputs, this output, or one of these named errors.
Zod
A runtime schema validation library used at HTTP route boundaries to reject malformed input before it reaches business logic.
Sequelize
The ORM used for typed database access; the contract mechanism for the data layer.
Fast-Track
The automated approval lane for low-amount, low-risk claims that bypasses the manual adjuster queue.
Risk Tier
A policy-level classification (1–5) reflecting historical loss and underwriting risk, used as a feature in claim risk scoring.
Reason Code
A machine-readable label (e.g. AMOUNT_UNDER_THRESHOLD) explaining why a triage decision was made, required for audit defensibility.
Audit Trail
The immutable, hash-verified record of every decision and its inputs, required for regulatory review of auto-approvals.
Correlation ID
A UUID generated at request entry and propagated through every log line and downstream call, so a failure can be traced end to end.
Technical Debt
A shortcut taken now that must be repaid later with extra effort; dangerous mainly when undisclosed.
Testing Pyramid
The target test mix: mostly fast unit tests, fewer integration tests, a thin layer of end-to-end tests.
DORA Metrics
Deployment frequency, change failure rate, mean time to restore, and lead time for changes — the industry-standard delivery performance signal.
Shadow Mode
A rollout phase where a new service computes and logs its decision but does not yet act on it, used to validate against a human baseline.
Canary Release
A rollout phase where a new feature is enabled for a small percentage of real traffic before general availability.
Squash Merge
A merge strategy that collapses a branch’s commits into one commit on the target branch, keeping history readable.
